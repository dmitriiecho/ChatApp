# Пагинация

[English version](../en/pagination.md) · [Все страницы](README.md)

Оба экрана показывают длинные списки: у пользователя больше 200 чатов, а в чате могут быть тысячи сообщений. Ни один экран не держит их все сразу. Каждый наблюдает за **окном** в кэше Room, а **пагинатор** в его Executor сдвигает окно, пока пользователь листает. В сеть пагинатор идёт, только когда в кэше нет того, на что сдвигается окно.

&nbsp;

## Одна идея на обоих экранах

Окна у экранов разной формы, потому что списки упорядочены по-разному:

| | Список чатов | Чат |
|---|---|---|
| Порядок | `sortKey`, который растёт с каждым новым сообщением в чате | `seq`: 1, 2, 3… в каждом чате, без пропусков |
| Окно | `offset` и `count` среди загруженных чатов | `fromSeq` и `toSeq` |
| Страница | 50 чатов | 50 сообщений |
| Максимум в окне | 150 чатов | 300 сообщений |
| Открывается | сверху | на первом непрочитанном или на самых новых сообщениях |
| Новое появляется | сверху: чаты поднимаются наверх | снизу: приходят новые сообщения |
| Дыры в кэше | никогда: чаты грузятся сверху вниз | бывают: у чата, открытого на первом непрочитанном, в кэше только кусок из середины |
| Пагинатор | `ConversationsPaginator` | `ChatPaginator` |
| Репозиторий | `ConversationsRepository` | `MessagesRepository` |

Зачем вообще окно? Room заново выполняет запрос при каждом изменении таблиц, которые тот читает. Чат с ботами меняется по нескольку раз в минуту, и каждый раз перечитывать тысячи строк было бы напрасной работой. С окном каждое перечитывание укладывается в несколько сотен строк, как бы далеко пользователь ни долистал; то, что ушло из окна, остаётся в Room и сразу возвращается.

&nbsp;

## Как экран просит ещё

Экран сам ничего не загружает. Он следит, где сейчас пользователь, и отправляет Intent, когда тот у края списка и за краем есть что-то ещё:

```kotlin
// ChatListScreen.kt
.collect { check ->
    if (check.isNearTop && check.hasAbove) currentOnIntent(ChatListIntent.ReachedTop)
    if (check.isNearBottom && check.hasMore) currentOnIntent(ChatListIntent.ReachedBottom)
}
```

- **«У края» — это ближе 10 элементов** до края (`EDGE_THRESHOLD`), поэтому следующая страница приходит раньше, чем пользователь долистает до конца.
- **Проверка повторяется, когда меняется окно или флаги**, а не только при прокрутке. После короткой страницы пользователь может остаться у края, и без этого список бы остановился. Список чатов следит за количеством чатов, а чат — за границами окна (самым новым и самым старым сообщением): окно из 300 сообщений, сдвинувшись на страницу, не меняет размер, и по количеству сдвиг был бы не виден.
- **Считаются элементы, а не строки.** Строка загрузки в конце появляется и пропадает с каждой попыткой; если бы её считали, без сети экран повторял бы попытки бесконечно.
- **Второй Intent, пока страница грузится, Executor пропускает** (`isLoadingMore`, `isLoadingOlder`, `isLoadingNewer`). Store работает на главном потоке, поэтому такая проверка надёжна и без блокировок (см. [Экраны](screens.md#store)).

Список сообщений в чате перевёрнут (`reverseLayout = true`): его первый элемент — самое новое сообщение, внизу у поля ввода. Поэтому «верх» чата — это конец его списка.

## Список чатов

### Что загружено

Кэш хранит чаты, загруженные сверху вниз без пропусков, а строка в `conversation_list_meta` говорит, докуда они загружены:

| Поле | Значит |
|---|---|
| `loadedDownToSortKey` | **граница загруженного**: самый маленький `sortKey`, загруженный сверху без пропусков |
| `hasMore` | у сервера есть чаты ниже границы |
| `syncToken` | токен синхронизации списка (см. [Синхронизация](sync.md#синхронизация-по-токену)) |

Запрос экрана читает только чаты выше границы, поэтому чат, который пришёл из сокета, но по порядку стоит далеко внизу, не появится посреди списка с дырой над ним:

```kotlin
@Query(
    """SELECT * FROM conversations
       WHERE sortKey >= (SELECT loadedDownToSortKey FROM conversation_list_meta WHERE id = 0)
       ORDER BY sortKey DESC LIMIT :limit OFFSET :offset""",
)
abstract fun observeLoaded(offset: Int, limit: Int): Flow<List<ConversationEntity>>
```

Репозиторий запрашивает на одну строку больше, чем вмещает окно: если она пришла, значит, в кэше есть что-то ниже, и отдельный запрос `COUNT` не нужен.

### Открытие

Список сам не загружает свою первую страницу: это делает синхронизация при первом подключении сокета (см. [Синхронизация](sync.md)). До этого экран показывает индикатор загрузки, потому что пустой кэш тогда значит «ещё не загружено», а не «чатов нет». Окно начинается с `(0, 50)`.

### Прокрутка вниз

`ConversationsPaginator.loadBelow()` расширяет окно на страницу, до 150 чатов, а дальше сдвигает его:

| Пользователь | Окно | Чаты |
|---|---|---|
| открывает экран | `(0, 50)` | 1–50 |
| листает вниз | `(0, 100)`, потом `(0, 150)` | 1–150 |
| листает дальше | `(50, 150)` | 51–200: первые 50 больше не отслеживаются |
| листает дальше | `(100, 150)` | 101–250 |

Прежде чем сдвинуть окно, пагинатор загружает чаты, на которые оно сдвинется:

```kotlin
suspend fun loadBelow() {
    val current = window.value
    val next = if (current.count + PAGE_SIZE <= MAX_WINDOW_SIZE) {
        current.copy(count = current.count + PAGE_SIZE)
    } else {
        current.copy(offset = current.offset + PAGE_SIZE)
    }
    ensureConversationsLoaded(count = next.offset + next.count)
    window.compareAndSet(current, next)
}
```

- **`ensureLoaded(count)`** грузит страницу за страницей ниже границы (`GET /conversations?beforeSortKey`), пока в кэше не наберётся столько чатов или пока они не кончатся на сервере. Если пользователь уже долистывал сюда раньше, чаты уже в кэше, и запросов нет вовсе.
- **Без сети он падает с `IOException`, и окно остаётся каким было**: откатывать нечего. Экран показывает снэкбар, а следующая попытка будет, когда пользователь снова начнёт листать.
- **`compareAndSet`**: если окно изменилось, пока грузилась страница, новое окно не затирается.

### Прокрутка обратно вверх

Всё, что выше окна, уже в кэше, поэтому `loadAbove()` только сдвигает окно на страницу вверх, без сети.

### Когда список меняется под окном

- **Чат поднимается наверх** с новым сообщением: его `sortKey` растёт, он проходит границу, и Room перечитывает окно. Если пользователь в самом верху, экран прокручивается за чатом (`FollowTop`, см. [Экраны](screens.md#списки-которые-растут-с-края)); если ниже — пользователь остаётся на своём месте.
- **Список начинается заново** (`resetRequired`) или чаты пропадают, пока окно далеко внизу: окно указывает туда, где чатов теперь нет, и пагинатор возвращает его наверх.
- **Страница из старого списка** приходит после того, как синхронизация начала список заново: граница за это время изменилась, поэтому страница отбрасывается, чтобы не оставить дыру, а следующая попытка загрузит правильную.
- **Пустая страница считается концом** списка, чтобы подгрузка не зациклилась.

## Чат

### Окно и голова

Окно — это два seq, и запрос никогда не перешагивает через дыру в кэше:

| Окно | Показывает |
|---|---|
| `fromSeq = 701, toSeq = 1000` | эти сообщения |
| `fromSeq = 951, toSeq = null` | **голову**: от 951 до конца сплошного участка, поэтому новые сообщения добавляются в неё сами |

Окно остаётся головой, только пока пользователь внизу чата. Как только он листает вверх, низ окна фиксируется, чтобы новые сообщения не сдвигали то, что он читает.

### Открытие

`ChatExecutor.onStart` открывает чат один раз, когда создаётся Store экрана:

1. **Если есть непрочитанные**, чат открывается на первом из них (`openAt(lastReadSeq + 1)`): страница вокруг него загружается, если её нет в кэше, а окно охватывает сплошной участок кэша вокруг него, до 25 сообщений в каждую сторону. Над ним ставится разделитель «Новые сообщения», и экран прокручивается к нему.
2. **Иначе** открываются самые новые сообщения из кэша, сразу и только из кэша (`openLatest`), как голова.
3. **Потом, в обоих случаях**, чат обновляется из сети (`refreshLatest`): сам чат, чтобы узнать его `lastSeq`, правки закэшированных сообщений и последняя страница. Новые сообщения, которые продолжают кэш, добавляются в голову сами.

Если чат давно не открывали, между кэшем и последней страницей есть дыра, и голова не может её перешагнуть. Тогда окно переезжает на последнюю страницу, но только если это всё ещё та голова, на которой пользователь остановился. Окно, открытое на первом непрочитанном, или окно, которое пользователь за это время пролистал, остаётся на месте, а вниз ведёт кнопка «к последним».

Без сети шаги 1–2 работают из кэша, а шаг 3 завершается ошибкой: чат остаётся на экране, а снэкбар объясняет, почему ничего нового не приходит.

### Прокрутка вверх

`loadOlder` запрашивает у репозитория 50 сообщений над окном. Репозиторий берёт их из кэша, если там есть все подряд, а иначе — с сервера (`beforeSeq`):

```kotlin
val targetSeq = max(1, beforeSeq - PAGE_SIZE)
val isCached = messageDao.count(conversationId, targetSeq, beforeSeq - 1) == (beforeSeq - targetSeq).toInt()
val error = if (isCached) null else tryNetwork { save(chatApi.before(conversationId, beforeSeq, PAGE_SIZE)) }
// Offline the window grows by as much as the cache has without a gap.
val newFromSeq = cachedDownFrom(conversationId, beforeSeq, notBelow = targetSeq)
if (newFromSeq == beforeSeq && error != null) throw error
```

- **Без сети окно растёт на столько, сколько есть в кэше** подряд; ошибка доходит до экрана, только если выше в кэше нет вообще ничего.
- **Окно перестаёт быть головой**: его низ фиксируется на самом новом показанном сообщении.
- **Если сообщений больше 300, отрезаются самые новые** — внизу, откуда пользователь ушёл:

```text
[701, 1000] пролистали вверх до 651  →  [651, 1000], 350 сообщений  →  [651, 950]
```

### Прокрутка вниз

`loadNewer` — то же самое вниз (`afterSeq`). Когда он доходит до конца чата (`lastSeq`), окно снова становится головой, и Executor сообщает о сообщениях, появившихся внизу, так же, как о новом сообщении (см. ниже). Если сообщений больше 300, отрезаются самые старые:

```text
[651, 950] пролистали вниз до 1000  →  [651, 1000], 350 сообщений  →  [701, 1000]
```

### Новые сообщения внизу

Страница, загруженная под окном в глубине истории, остаётся ниже экрана: список сохраняет место пользователя, и тот долистывает до неё сам. Прокручиваться за новыми сообщениями список должен, только пока окно — голова.

Новое сообщение из сокета попадает в кэш, только если продолжает его (`seq == maxSeq + 1`), поэтому оно добавляется в голову. Когда голова вырастает больше 300, отрезаются её самые старые сообщения, далеко над экраном. Если пользователь не дальше трёх сообщений от низа, экран прокручивается к новому; если он читает выше, его место сохраняется.

### Прыжки

| Прыжок | Делает |
|---|---|
| **Кнопка «к последним»** | видна, пока ниже окна есть сообщения (`hasNewer`); открывает самые новые сообщения из кэша как голову, прокручивает вниз, потом обновляет из сети |
| **Отправка из глубины истории** | то же: чат переходит в конец, где появится отправленное сообщение |
| **Кнопка в тулбаре** | открывает окно вокруг случайного сообщения из истории, обычно ещё не закэшированного, поэтому прокрутка в обе стороны грузит сообщения из сети; кнопка нужна, чтобы попробовать пагинацию |

### Гонки

Пагинатор работает на главном потоке, но на время загрузки он приостанавливается, а окно за это время может измениться: прыжок, новое сообщение, прокрутка в другую сторону. Два правила не дают запоздавшему ответу сломать окно:

- **Загрузка применяется только к тому окну, с которого началась.** В конце она сравнивает текущее окно с тем, что прочитала в начале, и ничего не делает, если они различаются.
- **Самое новое показанное сообщение берётся, только если его прочитали для текущего окна.** Сразу после прыжка экран ещё мгновение показывает сообщения старого окна, и если взять их, получилось бы окно, которое заканчивается раньше, чем начинается.

&nbsp;

## Почему не Paging 3

Paging 3 с `RemoteMediator` рассчитан на ленту, которая грузится с одного конца без дыр. Чату нужны дыры в кэше, голова, которая растёт сама, когда приходят сообщения, и открытие на любом сообщении; списку нужна пересортировка, когда чаты поднимаются. Всё это умещается в два небольших класса поверх Room: в `ConversationsPaginator` около 35 строк кода, в `ChatPaginator` около 120.
